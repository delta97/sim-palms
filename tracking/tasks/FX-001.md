## Goal

Find out whether ReShade can read the MSFS 2024 depth buffer while photogrammetry streams, and under which settings. This is the kill switch for the whole experiment: without depth there is no Stage A capture and no Stage B.

## Context

- ReShade can expose the depth buffer to effects and add-ons, but turns depth access off when it detects network activity it treats as multiplayer. MSFS 2024 streams photogrammetry constantly, so it may trip this. Nobody has checked yet.
- Blobs only exist with online photogrammetry ON, so "offline mode" is not a fix. It only tells us whether network traffic is the trigger.
- Results feed FX-007 (capture settings), FX-005 (depth flags), FX-025 and FX-021 (Stage B).
- Do not invent ReShade behaviour. Write down what you observe, with ReShade version and sim build.

## Steps

1. Record the MSFS 2024 build (as shown in the sim) and install the current ReShade release for the sim's DX12 executable. Record ReShade version and build type (standard or "full add-on support"). VERIFY: which executable ReShade must target.
2. Load a test flight over the DEC-004 block (or any photogrammetry city if DEC-004 is not decided), clear weather, noon.
3. Enable `DisplayDepth.fx`. Adjust the Generic Depth add-on settings (buffer selection, "copy before clear" style options as offered) and the `RESHADE_DEPTH_INPUT_IS_REVERSED`, `RESHADE_DEPTH_INPUT_IS_UPSIDE_DOWN`, `RESHADE_DEPTH_INPUT_IS_LOGARITHMIC` preprocessor values until depth looks right (near = one end of the range, sky consistent). Record the values and what the sky reads as.
4. Run the condition matrix from the plan_ref and record each cell: online data + photogrammetry ON with multiplayer OFF; same with multiplayer ON; offline mode. For each: depth visible yes/no, any ReShade overlay message about network or depth, screenshot of the overlay message if present (keep locally, describe in text).
5. With depth working: compare depth vs back-buffer resolution with TAA or DLAA at 100 % render scale, then with DLSS upscaling. Toggle frame generation and note whether depth still lines up with colour (pan the camera, watch edges).
6. VERIFY: whether the "full add-on support" build changes the network lockout. Note any guidance on using it with online services, citing the source.
7. Check the screenshot settings: does a "save before and after" option exist, what are the two file names, PNG format and bit depth, and roughly how many screenshots per second it sustains (hold a timer, press repeatedly, count files).
8. Write `palmfx/docs/depth-access.md`: verdict line first (`DEPTH-OK`, `DEPTH-OK-WITH: <config>`, or `DEPTH-UNAVAILABLE`), then versions, matrix, flags, resolution findings, screenshot findings, and VERIFY items still open.

## Acceptance criteria

- [ ] `palmfx/docs/depth-access.md` exists and starts with one of the three verdicts.
- [ ] Matrix has all three network conditions filled in with observations, not guesses.
- [ ] ReShade version, build type, sim build, depth flags and Generic Depth settings recorded.
- [ ] Depth resolution under DLAA/TAA vs DLSS, and the frame-generation observation, recorded.
- [ ] Screenshot "before and after" availability, naming and approximate throughput recorded.
- [ ] If the verdict is `DEPTH-UNAVAILABLE`, a log line is added to FX-100 saying Stage A ends NO-GO-C0.

## Verification

Manual: a reviewer reads `palmfx/docs/depth-access.md` and checks every matrix cell has an observation and the verdict matches the matrix.

```bash
head -5 palmfx/docs/depth-access.md   # first line contains DEPTH-OK, DEPTH-OK-WITH or DEPTH-UNAVAILABLE
grep -c "VERIFY" palmfx/docs/depth-access.md   # remaining unknowns are listed, not hidden
```
